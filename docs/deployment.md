# Установка и сопровождение

## Требования

Docker Engine или Docker Desktop с Linux containers и Docker Compose v2.
Для внешнего доступа нужны домен и HTTPS reverse proxy.

## Настройка

1. Скопируйте `.env.example` в `.env`.
2. Укажите собственный `POSTGRES_PASSWORD`. Готового пароля нет.
3. Заполните `BITRIX_WEBHOOK_URL`: адрес входящего вебхука с правами CRM.
   Пользователь вебхука должен иметь доступ к нужным лидам.
4. Укажите `AUTH_PUBLIC_ORIGIN`: внешний HTTPS-адрес сервиса без пути.
5. Оставьте `AUTH_COOKIE_SECURE=true` для HTTPS.
   При локальной разработке через HTTP задайте `false`.
6. При необходимости задайте `BITRIX_FIELD_MAP` — соответствие атрибутов
   квалификации реальным пользовательским полям вашего портала.

Не публикуйте `.env`, адрес вебхука, пароли и резервные копии базы.

```powershell
Copy-Item .env.example .env
# Заполните .env перед запуском.
docker compose up --build -d
docker compose exec api python -m app.users create admin --role admin
```

Команда создания администратора запрашивает пароль без вывода на экран.
Остальных пользователей добавляет администратор в разделе **Пользователи**.
Логин: 3–64 латинских символа, цифры, точки, дефисы или подчёркивания.
Пароль: 12–128 символов.

Локальный интерфейс: `http://localhost:3000`, описание API: `http://localhost:8000/docs`.
Compose применяет миграции перед запуском API. Порты привязаны к loopback-интерфейсу;
для публикации направьте внешний HTTPS proxy на веб-интерфейс.
Прокси и приложение должны использовать один origin и передавать исходный Host.
Проверьте вход и ссылки приглашений на внешнем адресе.

## Подключение Битрикс24

Используется CRM с лидами. Входящий вебхук хранится только на сервере.
Список полей читается из портала; пользовательские коды не зашиты в приложение.

В **Автообработке** выберите поле с текстом заявки. При ручном анализе можно
выбрать другое поле для конкретного запроса. Поле должно содержать одно текстовое
значение. HTML и BBCode преобразуются в обычный текст.

Для записи задайте `BITRIX_FIELD_MAP` в `.env`. Ключи:
`category`, `users`, `budget_min`, `budget_max`, `currency`, `deadline_text`.
Значения — существующие коды пользовательских полей `UF_CRM_` вашего портала.
Каждому атрибуту нужно отдельное поле подходящего типа.
Без соответствий анализ доступен, запись отключена.

После изменения `.env` пересоздайте API:

```powershell
docker compose up -d --force-recreate api
```

Запись выполняется только после подтверждения выбранных полей. Сервис проверяет,
что текст и значения в CRM не изменились после анализа. При изменении загрузите
лид заново. Если результат записи неизвестен, сначала проверьте CRM; повторная
запись не выполняется автоматически.

## Обработка новых лидов

Администратор включает отслеживание и выбирает получателя результатов.
При первом включении существующие лиды пропускаются. После паузы будут найдены
лиды, созданные за время остановки. Повторный анализ изменённых старых лидов
запускается вручную по ID.

Фоновая проверка выполняется в процессе API (`MONITOR_WORKER_ENABLED=true`).
Очередь и положение проверки хранятся в базе. Чтение временно недоступного лида
повторяется с задержкой; после пяти неудач доступен ручной повтор.
Уже созданные задания сохраняют выбранного при постановке получателя.

## Анализ и приоритет

`EXTRACTOR=rules` использует правила извлечения. `EXTRACTOR=llm` обращается
к настроенному провайдеру; для него задайте `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
Провайдер должен поддерживать Chat Completions и строгую JSON Schema.
Сервис проверяет, что подтверждающие цитаты присутствуют в исходном тексте.
При ошибке провайдера готовый результат не подставляется.

Приоритет определяется правилами: соответствие услугам — 2 балла,
подтверждённая нижняя граница бюджета не меньше `PRIORITY_BUDGET_THRESHOLD_RUB` —
1 балл, конкретные требования к пользователям или интеграциям — 1 балл.
От 4 баллов приоритет повышенный. Порог бюджета настраивается в `.env`.
Окончательную проверку фактов выполняет сотрудник.

## Данные и доступ

База хранится в Docker volume. `docker compose down` сохраняет данные.
Настройте резервное копирование PostgreSQL и проверьте восстановление перед
использованием с рабочими данными. В репозитории нет базы и готовых аккаунтов.

Менеджеру доступны только его результаты; администратору — все.
Пароли хешируются scrypt; сессии хранятся в HttpOnly cookie, в базе — хеши токенов.
При изменении роли или отключении сотрудника его доступ отзывается.
Ссылки установки пароля одноразовые и действуют ограниченное время.
Сервис не отправляет приглашения: администратор передаёт ссылку сотруднику.

Для сброса пароля первого администратора:

```powershell
docker compose exec api python -m app.users set-password admin
```

## Разработка и проверки

Python 3.12+, Node.js 24, pnpm 11.25.0. Установите зависимости из lock-файлов.
Для запуска Python вне Compose требуется `DATABASE_URL` вашей базы.
При необходимости URL-кодируйте пароль в строке подключения.

```powershell
python -m pip install -r requirements-dev.lock
python -m alembic upgrade head
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

В другом терминале:

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Для другого адреса API используйте `API_PROXY_TARGET`. По умолчанию локальный
Vite проксирует запросы на порт 8000; в Compose проксированием занимается Nginx.

```powershell
python -m ruff check app tests scripts migrations
python -m ruff format --check app tests scripts migrations
python -m pytest -q
pnpm --dir frontend format:check
pnpm --dir frontend test
pnpm --dir frontend build
```

Тесты используют отдельные временные базы и изолированные ответы внешних сервисов.
Тестовые данные не используются рабочими маршрутами.
`python -m scripts.smoke` проверяет мигрированную базу и удаляет созданные им записи;
выполняйте его на отдельной проверочной базе.
CI проверяет миграции на PostgreSQL 16 и собирает образы приложения.

`/health/live` проверяет процесс, `/health/ready` — базу и наличие миграций.
Адреса вебхуков содержат секрет, поэтому журналирование URL исходящих запросов
отключено. Для диагностики интеграции используйте коды ошибок без секретных URL.
